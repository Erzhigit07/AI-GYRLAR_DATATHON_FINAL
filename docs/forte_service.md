# Локальный сервис ForteBank

> Публикация 18.10.2026: для чистой установки используйте актуальный раздел запуска
> в [README](../README.md) и `scripts/download_forte_runtime.py`. Рабочие prompt,
> правила и runner/parser теперь включены в `configs/forte_deployment/`.
> Исторические метрики ниже рассчитаны по исходной разметке, которую пользователь
> впоследствии отклонил; они не подтверждают текущее качество. Актуальное сравнение
> по ручным меткам: [отчёт](../reports/forte_qwen_manual_check.json).

Сервис запускает одну локальную Qwen, веб-страницу и API из задания. Веса рабочей
модели не дообучались. Отдельный QLoRA-пилот завершён и сохранён, но не подключён
к API из-за отсутствия улучшения на уровне видео; итог —
`reports/forte_qwen_finetune_check.json`. Рабочая конфигурация использует overlap=6: на 32 development-видео
TP=2, TN=14, FP=1, FN=15, accuracy=0.50, recall=0.1176, F1=0.20. Вариант выбран
по большему recall/F1; прежний overlap=2 давал TP=1, TN=15, FP=0, FN=16,
recall=0.0588, F1=0.1111. При этом найдены два новых TP, потерян прежний TP и появилась
одна ложная тревога. Качество остаётся недостаточным; готовность к соревнованию
не подтверждена. Подключение API само по себе качество модели не улучшает.

Оба прогона полностью завершены на одинаковых видео и кадрах, без изменения весов,
инструкции и правил. Сравнение: `reports/forte_overlap_comparison.json`, журнал:
`reports/experiments.csv`. Это подбор на development, не независимая оценка holdout.

## Запуск на этом ноутбуке

Все команды выполняются из корня репозитория. Подготовленная среда уже содержит
необходимые зависимости:

```powershell
& 'outputs/forte-api-validation/20261018/.venv/Scripts/python.exe' -B -m src.forte.service --check
& 'outputs/forte-api-validation/20261018/.venv/Scripts/python.exe' -B -m src.forte.service
```

Открыть `http://127.0.0.1:8000`. Ключ доступа находится только в локальном файле
`outputs/forte-service/operator-key.txt`; в журнал и HTML он не выводится.
Его нужно вставить в поле «Ключ доступа» на экране входа и нажать «Войти».
Сервер проверяет ключ до открытия рабочего экрана, независимо от готовности модели.
Вместо файла можно установить
`FORTE_API_KEY` в среде процесса до запуска. Не коммитить и не публиковать ключ.

Если используется новая среда, установить `requirements-forte-service.txt`.
Веса и llama.cpp уже расположены локально; их пути и SHA берутся из сохранённого
эксперимента. Сервис ничего не скачивает при обработке видео. Для переноса на
другую ОС нужны совместимый runtime, веса и проверенная конфигурация; текущая
команда модели использует Windows/Vulkan и не является готовой Linux-инструкцией.

`configs/forte_service.example.json` задаёт конфигурацию эксперимента, локальные
порты, HTML и каталог результатов. Пути внутри JSON отсчитываются от репозитория,
независимо от текущего каталога терминала. `--config` позволяет выбрать другой JSON.

Для другой проверенной версии модели можно задать `weights_manifest` и
`weights_manifest_sha256` вместе. Манифест должен содержать ту же `revision`, что
`model_revision` эксперимента, и SHA-256 обеих частей модели в `files`. Перед
запуском проверяются сам манифест и веса; контрольные суммы сохраняются в
`service_metadata.json`. Это позволяет подготовить 4B, сохранив исходный манифест
2B. Подготовка через `--check` не запускает GPU и не подтверждает качество модели.

Для отката сначала остановить текущий сервис и запустить ту же команду с
`--config configs/forte_service.baseline.json`. Обе конфигурации ссылаются на отдельные
копии настроек, prompt/rules и кода в `outputs/forte-service/deployments/20261018/`.
Исходные конфигурации экспериментов не переписаны; в копиях сохранены путь/SHA
оригинала и путь к его оценке. Проверено, что все параметры алгоритма совпадают,
а SHA источников корректны. Дальнейшая правка рабочего prompt другого чата не
меняет эти копии и уже запущенную модель.

## Как устроен запуск

1. Проверяются SHA модели, runtime, инструкции, правил и исходников эксперимента.
2. В новый `outputs/forte-service/<run>/` копируются runner/parser и настройки.
   Существующие эксперименты не переписываются.
3. Проверяется свободный порт и отсутствие другого `llama-server`.
4. Модель запускается один раз на `127.0.0.1:8777`; все слои и vision projector
   используют GPU согласно проверенной конфигурации. Отдельный внутренний токен
   модели живёт в памяти процессов.
5. API запускается на `127.0.0.1:8000`. Он принимает одну активную загрузку/задачу;
   следующая получает 429. Это ограничивает очередь в пределах пяти минут.
6. Изолированный API-worker выполняет frozen runner синхронно. Результат проходит
   существующую проверку; JPEG извлекаются из загруженного видео самим сервером.
7. Незавершённый анализ, таймаут и ошибка возвращаются как `failed`, а не как
   отрицательное предсказание. Для извлечения доказательств резервируются 20 секунд.

Watchdog перезапускает только процесс модели, созданный этим сервисом, после
зависшего/неудачного транспортного запроса. При перезапуске новые загрузки получают
503. После трёх последовательных безуспешных восстановлений или критического
недостатка RAM модель отключается; успешный проверенный ответ обнуляет счётчик.
Причина сохраняется в `runtime_error.json`, ложный успешный ответ не выдаётся.

Остановка — Ctrl+C в терминале запуска. Завершается собственная модель и API.
Файл `service.lock` предотвращает второй экземпляр. После аварийного завершения
нужно проверить PID из блокировки и отсутствие прежнего сервиса, прежде чем
вручную убирать оставшуюся блокировку. Чужие процессы автоматически не завершаются.

## Интерфейс и API

- `/`: вход по ключу, загрузка MOV, статус, видео, результат и окно Explainable AI.
- `GET /api/v1/auth/check`: проверка `X-API-Key`, ответ `{"authenticated": true}`
  или 401; не запускает анализ и не создаёт задачу.
- `/healthz`: техническая готовность модели; ключи и пути не возвращаются.
- `/api/v1/rules`: только названия поддерживаемых правил и публичные источники.
- `POST /api/v1/analyze`: multipart `file`, заголовок `X-API-Key`, ответ 202/job_id.
- `GET /api/v1/jobs/{job_id}`: тот же ключ, состояние processing/done/failed.

На странице ключ хранится только в памяти открытой вкладки, не в URL, cookie или
local/sessionStorage. После входа поле очищается. Перезагрузка страницы и «Выйти»
требуют повторного входа. Выход удаляет локальное видео, результаты и ключ из
состояния страницы, останавливает опрос; уже отправленная серверная задача может
продолжиться. Каждый запрос анализа/статуса по-прежнему проверяет ключ на сервере.
Ответ 401 возвращает на экран входа. Видео не отправляется
до нажатия кнопки. После сбоя опроса повторяется только получение статуса, а не
загрузка. Локальные object URL исходного видео не публикуются сервером. Модельные
описания выводятся как текст; изображения принимаются только в формате JPEG.
Окно Explainable AI показывает описание события из ответа модели, извлечённые
сервером кадры и источник соответствующего правила. Оно не добавляет выдуманные
проценты уверенности, карты внимания или скрытые рассуждения модели.

Внутренний сервис и публичный адрес — разные проверки. `127.0.0.1` доступен только
на этом ноутбуке. После явного разрешения пользователя запущен временный HTTPS URL
через Cloudflare; инструкция и численные проверки — [forte_tunnel.md](forte_tunnel.md).
Модель работает на ноутбуке, порт модели не опубликован. Видео, ключ и результаты
при внешнем обращении проходят через Cloudflare. Интерфейс ограничивает MOV
95 000 000 байт (95 МБ), оставляя запас для внешнего прокси; внутренний API сохраняет
предел 128 MiB. Проверка с другого устройства через другую сеть ещё не выполнена.

## Проверки

```powershell
New-Item -ItemType Directory -Path outputs/forte-service-tests -Force | Out-Null
& 'outputs/forte-api-validation/20261018/.venv/Scripts/python.exe' -B -m pytest tests/forte -q -p no:cacheprovider --basetemp outputs/forte-service-tests/final-check
& '.venv/Scripts/python.exe' -B -m ruff check src/forte tests/forte experiments/forte_qwen_baseline.py --no-cache
```

Для каждого нового запуска pytest выбирайте новый `--basetemp`. Все fixtures
синтетические; они проверяют код, но не качество распознавания. Реальный API smoke
проверяет development-видео отдельно; его приватные JSON и изображения остаются
в ignored `outputs/forte-service-tests/`. Не использовать holdout для настройки.

Браузерные проверки входа, выхода, отказа доступа, Explainable AI и мобильной
вёрстки: `node tests/forte_ui/check_ui.cjs`. Нужны Node.js, доступный модуль
`playwright` и Chromium. Можно указать установленный браузер через `CHROME_PATH`,
а каталог модулей через `NODE_PATH`. Скрипт перехватывает запросы в браузере и
использует только синтетические ответы; он не обращается к рабочему сервису и
не запускает модель. Скриншоты сохраняются в `outputs/forte-ui-tests/browser/`.

### Что соответствует этапам ML

Данные собраны, проверены и разделены по уникальным видео: development=32,
holdout=8. Используется готовая Qwen3-VL-2B; обучение весов и дообучение не
проводились. Оцениваются инструкция, правила и параметры выбора кадров.
Development используется для таких сравнений; holdout должен оставаться закрытым
до выбора окончательной конфигурации. API выполняет предсказания локально.

Численный разбор baseline показал, что все 17 размеченных моментов в 16 пропущенных
видео присутствовали среди выбранных кадров. Для 8 из 17 моментов не было одного
локального окна с минимум двумя секундами контекста с обеих сторон. Это гипотеза
для эксперимента с перекрытием окон, а не установленная причина всех пропусков.
Сводка: `outputs/forte-service-audit/20261018/schema_v2_numeric_diagnosis.json`.

Покрытие двух активных правил эталонной разметкой остаётся **UNKNOWN**: в
проверенных источниках есть бинарный класс и время, но нет структурированного
`rule_id` или типа нарушения. Нельзя считать все 17 положительных видео
неподдержанными или использовать ответы модели как эталон типов. Для анализа
покрытия нужна локальная ручная разметка «активное правило / другой тип / неясно».

## Координация

### Проверка локального кандидата 4B

На RTX 4060 Laptop технический тест 16 синтетических кадров прошёл: загрузка
9,516 с, один запрос 7,156 с, наблюдаемый максимум занятой памяти всего GPU
4785 MiB. Это не оценка точности на видео. После освобождения RAM выполнен smoke
на двух коротких development-видео (по одному каждого бинарного класса).
Оба завершились `incomplete`: в 7 запросах были 4 complete-окна и 3 uncertain.
Незавершённые результаты не преобразовывались в `no_violation`; accuracy/recall/F1
не определены. Весь smoke занял 53,984 с; минимум свободной RAM — 0,133 GiB.
Из этого замера нельзя заключать, что именно нехватка памяти вызвала uncertain.

Условие 2/2 complete перед полным прогоном не выполнено, поэтому полный 4B на
32 видео **NOT RUN**. В API восстановлена прежняя 2B overlap6. Конфигурация 4B
сохранена отдельно и не активирована. Численный отчёт:
`outputs/forte-local/20261017-qwen/violation-baseline/20261018-qwen4b-overlap6-prepared/smoke/run_summary.json`.

### Отдельная подготовка GPU в Brev

18 октября пользователь разрешил до $12 из имеющихся Brev-кредитов. Подготовлена
отдельная L40S 48 ГБ для **синтетического теста**, а не для обработки конкурсных
данных. FAQ официального задания запрещает загружать видео во внешние облачные
сервисы; отдельного разрешения организаторов на Brev не получено. Видео, кадры,
описания событий и конкурсные предсказания в эту VM не передавались.

`scripts/brev_public_gpu_smoke.py` сам рисует 16 кадров 464×848 и скачивает только
публичные Qwen3-VL-4B/8B GGUF и llama.cpp с зафиксированными ревизиями/SHA-256. Команда
`--check` проверяет подготовку запроса без сети/GPU. Этот тест не оценивает качество
распознавания конкурсных нарушений и не меняет работающую локальную модель.

На выданной VM готовый Ubuntu-архив b11669 не запустился: требуется GLIBC_2.38,
а установлена glibc2.35. `scripts/build_brev_llama.sh` сохраняет воспроизводимую
сборку того же commit `620d2225cc436ab0b001e3200e590e3b286ef9ab` для CUDA12.6/sm89.
Синтаксис Bash и Python/Ruff проверены локально. Сборка завершилась, обе модели
успешно ответили на одинаковый синтетический запрос: красный прямоугольник,
движение вправо, `synthetic=true`. Время одного HTTP-запроса: 8B — 2,209 с,
4B — 1,537 с; загрузка весов и запуск сервера в это время не входят.
После запроса `nvidia-smi` показал 7715 MiB для 8B и 5279 MiB для 4B — это
снимки памяти, не пиковые значения. Каждый вариант проверен одним запросом;
из этих измерений нельзя выводить качество на конкурсных видео или скорость
на ноутбуке с Vulkan. Отчёт: `outputs/forte-brev/20261018/smoke-comparison.json`.
Первый запуск 4B сразу после 8B завершился ошибкой занятого порта до запуска
модели; после проверки отсутствия слушателя отдельный повтор прошёл успешно.

Скрипт завершает только созданный им процесс модели. Он **не останавливает VM**;
её необходимо остановить отдельно. При фактическом развёртывании Brev показал
256 ГиБ диска и $1,77/час вместо выбранных в форме 128 ГиБ/$1,76. После остановки
вычислений остаётся плата за хранение $0,03/час. Состояние **Stopped** подтверждено
18 октября в 00:57:12 UTC; от создания прошло 19 мин 45 с. Позднее Brev Billing
в разрезе этой VM показал **$1,13**: $1,11 вычисления и $0,02 хранение. Это сумма
в интерфейсе учёта, а не окончательный счёт; она заменяет предварительную оценку
$0,58 по времени. Лимит пользователя $12 соблюдён. После подтверждения
пользователя VM и диск удалены; страница Compute показывает `No compute resources`.

### Распределение работ между чатами

Чат «Datathon NU» владеет baseline, правилами, экспериментами и улучшениями модели.
Чат «1» проверяет результаты. Чат «Проверь ML-процесс проекта» владеет новыми
`local_analyzer.py`, `service.py`, их тестами, этой инструкцией, конфигурацией и UI.
Перед следующим GPU-экспериментом согласовать остановку сервиса. Новую конфигурацию
подключать после сравнимой оценки, сохраняя старую версию для отката.
