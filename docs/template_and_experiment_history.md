# Datathon-AI-GYRLAR — DATATHON 2026

Универсальный Python-шаблон для локального анализа таблиц и проверяемых ML-экспериментов.
Текущий кейс ForteBank относится к анализу видео. Для него добавлен отдельный
[локальный API, проверка доказательств и оценка](docs/forte_local.md).
Qwen подключена к API: загрузка MOV, статус, результат, таймкоды и кадры из исходного
видео проверены локально. Запуск модели и интерфейса описан в
[инструкции сервиса](docs/forte_service.md), внешний HTTPS-доступ — в
[инструкции туннеля](docs/forte_tunnel.md). Рабочий API использует исходные локальные веса.
Отдельный QLoRA-пилот Qwen3-VL-2B дообучен и сохранён, но не подключён к API:
улучшение на внутренних проверочных видео не подтверждено. См. раздел
[дообучения](#пилот-дообучения-qwen3-vl) и
[отчёт](reports/forte_qwen_finetune_check.json). Качество обнаружения baseline пока недостаточное,
готовность к сдаче не подтверждена. Titanic и House Prices остаются учебными репетициями.
Правила проекта: [AGENTS.md](AGENTS.md); условия организаторов имеют приоритет.

## Локальная установка

Python 3.11 или 3.12. Все команды выполняйте из корня проекта.

```bash
git clone https://github.com/Erzhigit07/Datathon-AI-GYRLAR.git
cd Datathon-AI-GYRLAR
git switch main
```

Для проверки ещё не объединённого PR переключитесь на его фактическую ветку или commit.

последующих изменений учебных репетиций.

```powershell

.\.venv\Scripts\python.exe -m pip install -r requirements-dev.txt
.\.venv\Scripts\python.exe -m pytest -q
.\.venv\Scripts\python.exe -m jupyterlab
```

Python 3.11/3.12 для `-m venv .venv`. При автоматизации нескольких рабочих копий
указывайте абсолютный путь к их `.venv/Scripts/python.exe`, чтобы не запустить другую среду.

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements-dev.txt
python -m pytest -q
```

## Автоматические проверки GitHub Actions

Workflow [CI](.github/workflows/ci.yml) запускается для Pull Request в `main`,
после push в `main` и вручную через **Actions → CI → Run workflow**.
Ручной запуск станет доступен после добавления workflow в основную ветку.

Матрица проверяет Python 3.12 на `ubuntu-latest` и `windows-latest`.
Каждая job устанавливает `requirements.txt`, `requirements-dev.txt` и
`requirements-catboost.txt` и `requirements-forte.txt`, затем выполняет:

```bash
python -m pytest -q
python -m ruff check .
python -m ruff format --check .
python -m pip check
python -m compileall -q src tests experiments
```

Тесты используют только синтетические fixtures во временных каталогах, включая
проверки CatBoost, исполнение EDA-ноутбука и созданные тестами короткие MOV/JPEG для API.
Локальные Titanic/House Prices и
конкурсные данные не нужны. CI не запускает учебные репетиции и не публикует прогнозы.

Используются официальные `actions/checkout` и `actions/setup-python`, закреплённые
по SHA, с правами `contents: read`. Кешируются только загрузки pip; ключ зависит
от четырёх requirements-файлов. Время каждой job ограничено 20 минутами.
Перед объединением PR проверяйте успешное завершение обеих jobs: локальный запуск
сам по себе не подтверждает успешную работу GitHub Actions.

## Загрузка и качество данных

После получения данных разместите оригиналы в `data/raw/`. Модули открывают их только
для чтения. CSV читается сначала как UTF-8; при ошибке декодирования определяется
предполагаемая кодировка с предупреждением. Для неоднозначных файлов задайте `encoding`
явно. Разделитель задаётся через `sep`, а значимые ведущие нули ID сохраняются через `dtype`.
Автоопределение кодировки — эвристика, которую нужно проверить визуально.
CSV с неожиданным неявным индексом или предупреждением об усечении полей отклоняется.
Если индекс предусмотрен форматом файла, задайте `index_col` явно.

В Python/ноутбуке, после задания собственного `data_path`:

```python
from src.data_loader import load_data
from src.quality import save_quality_report

frame = load_data(data_path)  # локальный CSV, XLSX или Parquet
# Для CSV при необходимости: encoding="cp1251", sep=";", dtype={id_column: "string"}
# Для XLSX: sheet_name="Имя листа"; читается одна таблица за вызов.
save_quality_report(frame, "outputs/quality/first_review")
```

Папка отчёта должна быть новой. Отчёт содержит размеры, типы, пропуски, дубликаты,
описательную статистику, константные/пустые столбцы, inf, IQR-выбросы и высокую
кардинальность. Числовая статистика исключает inf, их количество указано отдельно.
Это признаки для проверки, а не готовые выводы о качестве: строки не удаляются,
выбросы не исправляются. Файлы читаются целиком в память; потоковое чтение не реализовано.

## EDA

Откройте `notebooks/eda.ipynb`, задайте `DATA_PATH`, при необходимости `TARGET` и
`READ_OPTIONS`, затем выполните ячейки. Пока путь не задан, ноутбук останавливается
с понятным сообщением. Датасеты не скачиваются и не генерируются.

Графики и отчёт сохраняются в отдельный `outputs/eda/<id>/`. Строятся гистограммы,
частоты top-категорий и Pearson-корреляции непостоянных числовых столбцов. Лимит
`MAX_COLUMNS` предотвращает бесконтрольную генерацию графиков; target показывается
дополнительно, если не вошёл в лимит. Числовые коды категорий требуют проверки смысла
и типов; корреляция не доказывает причинность. Поля выводов заполняйте по реальным
наблюдениям. Перед коммитом очистите выводы, содержащие данные.

## Конфигурация и обучение

Скопируйте `configs/template.json` в собственный JSON и заполните:

| Поле | Что задать после изучения задания |
| --- | --- |
| `data_path`, `dataset_label` | Локальный файл и ссылка на источник/версию данных |
| `task`, `target` | `classification` / `regression` и реальная цель |
| `features` | Явный список доступных при прогнозе признаков после проверки утечек |
| `id_column` | Уникальный ID или `null`; сохраняется в предсказаниях |
| `validation` | `random`, `group` или `time`, выбранный по структуре данных |
| `group_column`, `time_column` | Только соответствующий выбранной стратегии столбец |
| `validation_size`, `seed` | Размер holdout и фиксированный seed |
| `metrics` | Непустой список применимых метрик, выбранных явно |
| `average`, `positive_label` | Усреднение classification-метрик и позитивная метка для binary |
| `models`, `model_params` | Только нужные кандидаты и их параметры |
| `target_transform` | `none` по умолчанию; `log` только для положительной цели регрессии |
| `read_options` | Настройки чтения: `encoding`, `sep`, `dtype`, `sheet_name` и т. п. |
| `output_dir`, `data_kind` | Папка запусков; `real` для реальных данных |

Пути относительны рабочей папке. Шаблон с `null` намеренно не запускает обучение.

```bash
python -m src.train --config configs/local.json
```

Baseline — наиболее частый класс или среднее target регрессии. Он всегда оценивается
на том же split, что и кандидаты. `models: []` запускает только baseline.
`linear` означает Logistic Regression для классификации и Linear Regression для регрессии;
`random_forest` — соответствующий Random Forest. `catboost` требует отдельной установки.
`ridge` — регуляризованная линейная регрессия (по умолчанию solver=lsqr для sparse-признаков).
Все алгоритмы автоматически не перебираются.

При явном `target_transform: "log"` применяется TransformedTargetRegressor: модель
обучается на натуральном логарифме цели, а predict автоматически возвращает исходный
масштаб через exp. Baseline в этом режиме — геометрическое среднее train-target.
Нулевые и отрицательные цели отклоняются. Без этого параметра поведение прежнее.

Внутри каждого Pipeline: сохранение пропусков и нормализация категорий → заполнение
числовых пропусков медианой и масштабирование → заполнение категорий модой и OneHotEncoder
с поддержкой неизвестных категорий → модель. Статистики обучаются **только на train**.
CatBoost использует этот же кодировщик для единообразия; нативный categorical-режим
можно добавить по результатам реального задания. One-hot на высокой кардинальности
может расходовать много памяти. Datetime и inf в признаках требуют явного решения.

### Валидация и ограничения защиты от утечек

- `random`: случайное разбиение; классификация стратифицирована.
- `group`: одна группа не попадает одновременно в train и validation.
- `time`: train строго раньше validation; равные timestamps не разделяются.
  Числовые epoch нужно предварительно преобразовать с явной единицей измерения.
- Target, ID и столбцы группы/времени исключены из разрешённых признаков.
- Пропуски target, пустой split и классы validation, отсутствующие в train, вызывают ошибку.

Автоматически распознать все утечки невозможно. Проверяйте происхождение и момент
доступности признаков. Если требуются одновременно группы и время, gap/embargo,
rolling validation или CV, нужно адаптировать `validation.py`: сейчас это один holdout.
Не подбирайте признаки и параметры по окончательному скрытому test. После многократного
сравнения моделей один и тот же holdout тоже может потребовать дополнительной проверки.

### Метрики и эксперименты

Классификация: `accuracy`, `precision`, `recall`, `f1`. Для последних трёх требуется
явное `average`: `binary`, `macro`, `micro` или `weighted`. Для `binary` задайте
`positive_label` нужного типа и проверьте наличие ровно двух классов. Неопределённые
precision/recall дают предупреждение sklearn и значение 0; оно не скрывается.

Регрессия: `mae`, `rmse`, `r2`, `log_rmse`. Последняя — RMSE натуральных логарифмов
положительных цен и прогнозов, **не log1p/RMSLE**; выбирается только явно. Неположительные
и бесконечные значения не обрезаются, а вызывают ошибку.
Для постоянного target validation или менее двух строк
R² отклоняется как неопределённая. Метрики другой задачи и пустой список не допускаются.
Официальную нестандартную метрику потребуется реализовать и проверить отдельно.

Каждый `outputs/experiments/<run-id>/` содержит:

- `config.json`, `metadata.json`: настройки, хеш исходных данных, версии среды,
  размеры split, параметры моделей и ограничения оценки.
- `warnings.json`: предупреждения fit/predict/метрик с именем модели; они также
  выводятся при запуске. Поле `phase` различает оценку `holdout` и итоговый `refit`.
  Это позволяет отличать условный ноль precision от определённой метрики.
- `metrics.csv`: выбранные метрики каждой модели, baseline и улучшение относительно него
  (положительное — лучше), время обучения, маркировка типа данных.
- `split.csv`: назначение каждой позиции исходной строки в train/validation.
- `validation_predictions.csv`: фактические значения и предсказания только holdout.
- `<model>.joblib`: pipeline, обученный на train-части.

Каталоги уникальны, старые результаты не перезаписываются. Фактические выводы переносите
в `reports/`; при необходимости ведите `reports/experiments.csv` с полным контекстом сравнения.
Конкурсные результаты до получения задания отсутствуют.

После обоснованного выбора модели можно явно переобучить её на всех строках:

```bash
python -m src.train --config configs/local.json --refit linear
```

Дополнительно сохранится `refit.joblib`. Метрики остаются оценкой модели на holdout,
а не оценкой итоговой модели. Для инференса используйте `src.predict.predict_frame`:
он сохраняет число/порядок строк, индекс и ID, проверяет схему и допустимость предсказаний.
Загружайте только доверенные joblib-файлы. Формат submission, вероятности классов и
пороги решения намеренно не предполагаются: они зависят от правил конкурса.

## Пилот дообучения Qwen3-VL

`src/forte/qwen_finetune_data.py` готовит отдельный бинарный эксперимент из локального
манифеста видео. Разделение выполняется по целым исходным роликам внутри development;
holdout-видео не декодируются. Положительные обучающие окна используют существующие
временные отметки, отрицательные берутся только из отрицательных роликов. При проверке
просматривается вся временная шкала, без выбора окон по правильному времени события.

```bash
python -m src.forte.qwen_finetune_data --data-root outputs/forte-local/20261017-qwen --output outputs/qwen_finetune/NEW_RUN/data
```

Для обучения требуется отдельная CUDA-среда. Установка закреплённых зависимостей
описана в `requirements-qwen-finetune.txt`; окружение работающего API не изменяется.

```bash
python scripts/qwen_finetune.py --data outputs/qwen_finetune/NEW_RUN/data --output outputs/qwen_finetune/NEW_RUN/training
python scripts/qwen_finetune_verify.py --data outputs/qwen_finetune/NEW_RUN/data --run outputs/qwen_finetune/NEW_RUN/training --paired-evaluation
```

Скрипт сравнивает исходный Qwen3-VL-2B и его QLoRA-адаптер на одинаковых проверочных
окнах, сохраняет веса и фактические метрики. Перепроверка сохранённого адаптера включает
повторную загрузку и одно фиксированное предсказание. Каталоги запусков не перезаписываются.
Скрипты не публикуют данные или модель в Hub и не переключают API автоматически.

Это обучение ответу `0/1`: типы нарушений, интервалы и объяснения требуют отдельной
проверенной разметки. Разделение исключает точные дубликаты; родственные камеры/смены
ещё не сгруппированы вручную. Development ранее просматривался, поэтому результат
является внутренней проверкой, а не независимой финальной оценкой. Облачный запуск
18.10.2026 выполнен как отдельный эксперимент по явному разрешению пользователя;
он не подтверждает соблюдение требования конкурса о локальной обработке.

Фактический пилот `20261018-qwen2b-qlora-pilot`: 24 обучающих видео (74 окна),
8 проверочных (57 окон), 3 эпохи / 57 шагов оптимизатора за 443,45 секунды на L40S.
8 финальных holdout-видео не читались и не загружались. Сохранённый адаптер успешно
загружен повторно; локальная копия всех 34 экспортированных файлов проверена по SHA-256.

При парном сравнении одной загруженной модели с выключенным и включённым адаптером
обе версии получили TP=4, TN=0, FP=4, FN=0: accuracy=0,5, precision=0,5, recall=1,0,
F1=0,6667. Улучшения на уровне целых видео нет, API продолжает использовать прежнюю
модель. Первый `before`-проход был выполнен до приведения замороженных весов PEFT
к другой точности; для выводов используются только `paired_base` / `paired_adapter`.
В текущем скрипте подготовка весов перенесена перед исходной оценкой.
Подробности: `reports/forte_qwen_finetune_check.json`, две строки эксперимента в

## Изолированные учебные репетиции

Конфигурации находятся в `configs/educational/`, скрипты — в `experiments/`,
отчёты — в `reports/educational/`, а датасеты и артефакты — в игнорируемых Git каталогах.
Результаты Titanic и House Prices не являются результатами DATATHON.
Для House Prices выбор модели выполняется по пяти фолдам только внутри train-части;
внешний holdout используется после фиксации выбора. Логика этой репетиции не меняет
универсальный способ разбиения по умолчанию.

Фактические результаты: [Titanic](reports/educational/titanic_results.md) и
[House Prices](reports/educational/house_prices_results.md). Последний отчёт содержит
аудит Titanic, метрики CV/holdout, ошибки прогнозирования и ограничения готовности.
Обычный запуск House Prices не требует данных или результатов Titanic. Разместите
предоставленные локальные файлы в `data/raw/house_prices/`, установите optional CatBoost
для этой конфигурации и выполните:

```bash
python -m src.train --config configs/educational/house_prices.json --refit catboost
```

Имя refit-модели задаётся явно; CLI не выбирает её по holdout. Для конфигурации без
CatBoost удалите его из `models` и `model_params` в отдельном JSON и задайте нужный refit.
Предсказания из нового каталога запуска получайте через `src.predict.predict_frame`.

Текущая локальная версия `test.csv` содержит разрешённую пользователем правку:
у `Id=2593` значение `GarageYrBlt` заменено с `2207` на `2007`. Этот файл **не идентичен
исходному Kaggle-файлу**. Его SHA-256:
`a7590d2adf95e0b70281c2b664be0623ff9bc9cf5ce9e4f3cd24f0e0eeefc14c`.
Исторический отчёт House Prices описывает запуск до правки; последующая проверка
с исправленным test описана в [отчёте готовности](reports/readiness_check.md).
Не заменяйте локальные данные оригиналом автоматически. Скрипт копирования в совместной
репетиции отклоняет несовпадающий существующий файл, сохраняя его содержимое.
Данные и прогнозы не входят в Git.

Следующая команда — **совместная репетиция House Prices и аудит Titanic**; только этот
сценарий требует сохранённых артефактов Titanic (также нужен optional CatBoost):

```bash
python -m experiments.house_prices_rehearsal --source-dir "путь/к/house-prices-advanced-regression-techniques" --titanic-result "путь/к/манифесту/Titanic/result.json"
```

Скрипт сохраняет новые каталоги запусков, проверяет SHA-256 источников, воспроизводимость,
