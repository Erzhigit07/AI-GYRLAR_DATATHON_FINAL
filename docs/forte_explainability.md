# Explainable AI: контракт бэкенда v1

Модель, веса, prompt, выборка кадров и правило классификации не меняются.
Бэкенд сохраняет фактические ответы окон существующего Qwen-анализатора,
связывает их с событиями и извлекает контекст из исходного видео. Нового запроса
к модели и обучения для объяснения нет. Бинарный QLoRA-адаптер сюда не подключён.

## Запрос фронта

После `POST /api/v1/analyze` и получения `status: done` от обычного polling:

```http
GET /api/v1/jobs/{job_id}/explanation
X-API-Key: <тот же ключ, которым отправлено видео>
```

Текущий `GET /api/v1/jobs/{job_id}` сохраняет прежние поля без изменений.
Новый endpoint возвращает HTTP 200 с одним из вариантов:

- `{"job_id":"...","status":"processing"}` — можно продолжить polling;
- `{"job_id":"...","status":"failed","error":{"code":"..."}}` — анализа нет,
  объяснения и отрицательного вердикта не создаём;
- `{"job_id":"...","status":"done","explanation":{...}}` — объект ниже.

HTTP 401 означает неверный/отсутствующий ключ, HTTP 404 — неизвестную, чужую
или уже удалённую задачу. Ответы endpoint имеют `Cache-Control: no-store`.
Просмотр объяснения не запускает повторный анализ и не обращается к GPU.

## Поля explanation

| Поле | Смысл / использование |
|---|---|
| `schema_version` | `1` |
| `status` | `available` — окна проверены; `partial` — доступны события и кадры, детализация окон отсутствует или некорректна |
| `verdict` | Тот же `violation` / `no_violation`, что в обычном результате |
| `kind` | `evidence_and_pipeline_trace` |
| `window_trace_available` | Можно ли показывать счётчики и список окон |
| `unavailable_reason` | `null` или `window_trace_unavailable`; пустой список при `partial` нельзя трактовать как отсутствие срабатываний |
| `aggregation` | Объект правила объединения ниже, либо `null` |
| `rule_ids` | Проверявшийся набор правил, либо `null`, если трасса недоступна |
| `triggered_window_ids` | ID всех сработавших окон, включая обзорные |
| `windows` | Все проанализированные окна в исходном порядке |
| `events` | События обычного результата с контекстом и ссылками на окна |
| `context_offset_sec` | `1.0`: целевые кадры за секунду до/после исходной метки события |
| `confidence` | Всегда `null`; проверенной вероятности нет |
| `limitations` | Короткие пояснения ограничений для отображения пользователю |

`aggregation` содержит:

- `method: any_event_after_all_windows_complete`;
- `verdict`, `expected_windows`, `completed_windows`, `positive_windows`, `negative_windows`;
- `distinct_events`, `returned_events`, `omitted_events`;
- `reason_code: window_triggered | no_windows_triggered`;
- `explanation` — готовый русский текст о том, как получился итог.

Действующее правило: все окна должны закончиться определённым ответом; хотя бы
одно событие в любом окне даёт положительный итог. Это **не голосование большинства**.
Одинаковые события (тип, время, описание) объединяются; в обычный результат
попадают первые 32, отсортированные по времени, типу и описанию. Все сработавшие
окна сохраняются, даже если их события не вошли в эти 32.

## Окна и события

Каждый элемент `windows`:

```json
{
  "window_id": "window-0002",
  "index": 2,
  "kind": "local",
  "start_sec": 0.75,
  "end_sec": 3.75,
  "frame_timestamps_sec": [0.75, 1.5, 3.75],
  "verdict": "violation",
  "triggered": true,
  "events": [{
    "type": "synthetic-rule",
    "timecode_sec": 1.5,
    "description": "Synthetic event",
    "result_event_index": 0
  }]
}
```

Это **синтетический пример формы ответа**, не результат распознавания человека.
`index` и `result_event_index` считаются с нуля. При `result_event_index: null`
событие находится за лимитом основного результата и не имеет отдельного
набора JPEG в `explanation.events`.

`kind` бывает `local` и `overview`. Границы означают первый и последний
**показанный модели кадр**, не начало/конец нарушения. У обзорного окна между
кадрами могут быть большие промежутки. `frame_timestamps_sec` — исходные PTS
относительно первого декодированного кадра. Окна могут перекрываться.

Каждый элемент `explanation.events` содержит:

- `event_index` — индекс в обычном `violations`;
- `type`, `timecode_sec`, `description` — соответствуют обычному результату;
- `description_source: model_output` — описание модели, не подтверждённая истина;
- `window_ids` — все окна, сообщившие именно об этом событии;
- `context_frames` — массив `{role, timestamp_sec, image_base64}`;
- `missing_context_roles` — отсутствующие `before` и/или `after`.

`role` равен `before`, `event` или `after`; кадры идут в этом порядке.
Рендер JPEG: `data:image/jpeg;base64,` + `image_base64`.
Для времени всегда использовать **`timestamp_sec`**, не вычислять его на фронте.
Центральный кадр совпадает с `violations[event_index].evidence_frames[0]`.
Кадры извлекаются сервером из того же неизменённого видео. Их получение не
означает, что именно эти контекстные кадры были входом модели.

На границах видео берётся ближайший доступный кадр. Если он совпал с центральным,
роль отсутствует и указана в `missing_context_roles`; кадр не дублируется под
вымышленным временем. Сдвиг ±1 секунда — способ показа контекста, не порог нарушения.

Для названия правила, источника и пункта использовать существующий
`GET /api/v1/rules`, соединяя `event.type` с `rule.rule_id`. Если правило неизвестно,
показать ID и «Источник не предоставлен», а не подставлять другое правило.

## Ограничения и совместимость

- Это проверяемая трасса решения сервиса, а не объяснение скрытых вычислений модели.
- Описание может ошибаться. Не добавлять проценты уверенности, bounding boxes или
  heatmap: API их не вычисляет.
- При `no_violation` объясняются окна и правило объединения; положительных событий
  и контекстных кадров нет. Это не подтверждение соблюдения всех возможных правил.
- При `partial` показать доступные кадры/описание и отсутствие детализации. Не
  реконструировать сработавшие окна из длины видео.
- Старые результаты не пересчитываются задним числом. Если `explanation: null`
  (например, у результата от старого исполнителя), показывать «Объяснение недоступно».
- Результаты и JPEG приватны, хранятся в памяти вместе с задачей: по умолчанию до
  часа, максимум 100 завершённых задач, общий лимит 64 МиБ; могут быть удалены раньше
  по лимиту. После перезапуска исчезают. Исходная загрузка удаляется после обработки.
- Дополнительные изображения входят в те же лимиты времени/размера результата.
- Требуется перезапуск API для загрузки нового Python-кода. Для новых объяснений
  видео нужно обработать после перезапуска. Модель и её конфигурацию заменять не нужно.

## Проверка

Новые тесты: `tests/forte/test_explanations.py`. Проверяют синтетические положительные
и отрицательные ответы, перекрывающиеся окна, объединение/ограничение событий,
деградацию при некорректной трассе, реальные JPEG/PTS, крайние кадры,
совместимость старого ответа, авторизацию и изоляцию задач.

В `tests/forte/test_local_analyzer.py` настоящий frozen worker проверяется на
синтетическом видео с подменой только HTTP-ответа модели; число запросов не меняется.
Эти проверки подтверждают работу бэкенда, **не качество распознавания нарушений**.

## Примеры по подтверждённой ручной разметке

Отдельный демонстрационный режим показывает заданные пользователем тип, время и
комментарий. Он не вызывает Qwen, не дообучает модель и не заменяет ответы
`POST /api/v1/analyze`. Все маршруты ниже требуют обычный `X-API-Key` и возвращают
`Cache-Control: no-store`:

- `GET /api/v1/examples` — список `{source: "human_annotation", model_generated:
  false, examples: [{example_id, video_id, title, timecode_sec, result_url,
  explanation_url, video_url}]}`.
- `GET /api/v1/examples/{example_id}` — обычные `job_id`, `status`, `verdict`,
  `violations`, дополненные `example_id`, `result_source: "human_annotation"`,
  `model_generated: false`, `source_label: "Размечено человеком"`.
- `GET /api/v1/examples/{example_id}/explanation` — те же сведения об источнике и
  `explanation.kind: "human_annotation_with_video_evidence"`. Есть настоящие
  `context_frames`, `description_source: "human_annotation"`, `rule_title` и
  `annotated_timecode_sec`. `windows: []`, `window_trace_available: false`,
  `confidence: null`; `aggregation.method: "manual_annotation"` и текст объясняют
  ручное происхождение решения. Окна или уверенность модели не выдумываются.
- `GET /api/v1/examples/{example_id}/video` — MOV с поддержкой Range. На фронте
  загружать через авторизованный `fetch` в Blob; ключ не передавать в URL.

Название брать из списка примеров или `events[].rule_title`: набор ручных примеров
может отличаться от активных модельных критериев `/api/v1/rules`.

Файлы готовит `scripts/prepare_manual_examples.py` из авторитетного набора ручной
разметки и проверенных исходных видео. Скрипт проверяет SHA256, копирует видеопоток
в MOV без перекодирования и извлекает кадры на времени метки и ±1 секунду.
Манифест задаётся через `manual_examples_manifest` в конфигурации сервиса.
Файлы остаются локальными, вне Git; произвольные пути из HTTP не принимаются.

Для показа без GPU установить `start_model: false`: API и примеры доступны,
`/healthz` сообщает `model_ready: false, manual_examples_available: true`, а
автоматический анализ возвращает 503. Значение по умолчанию при отсутствии поля —
`true`; включение обратно требует свободной памяти и перезапуска сервиса.

Подготовленные примеры: X-20/5 с (сейф), X-33/5 с (дверь), X-40/5 с (верхняя
одежда), X-46/13 с (постороннее занятие при неубранных деньгах). Это демонстрация
ручной разметки и извлечения доказательных кадров, не оценка качества модели.
