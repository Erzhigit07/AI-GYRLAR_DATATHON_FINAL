# Временный HTTPS-доступ для жюри

Скрипт `scripts/start_forte_tunnel.ps1` подготовлен для ноутбука без сервера и
домена. Он направляет временный адрес `https://….trycloudflare.com` только на
`http://127.0.0.1:8000`. Qwen продолжает работать на ноутбуке; порт модели 8777
не публикуется. Данные HTTP-запросов, включая видео, `X-API-Key`, результаты и
кадры-доказательства, при внешнем обращении проходят через инфраструктуру
Cloudflare. Это внешний маршрут передачи данных, а не внешний AI API.

18 октября 2026 пользователь явно согласовал этот маршрут: видео, результаты и
ключ проходят через Cloudflare, inference остаётся на ноутбуке; первая внешняя
проверка выполняется на синтетических данных. Такое согласование получено для
текущего запуска. Скрипт сохраняет явный флаг `-AllowExternalTraffic`, а
`-CheckOnly` обращается исключительно к локальному API и не создаёт внешний адрес.
Согласие пользователя на маршрут само по себе не подтверждает соответствие всем
конкурсным правилам о передаче данных.

## Что подготовлено

В `outputs/forte-tunnel/tools/cloudflared-windows-amd64.exe` сохранён официальный
Windows amd64 binary **2026.10.1**. Его SHA-256 сверяется при каждом запуске:

```text
4d2490e74082c5d48dbfedaf92576fa5bd1702379ab88eb7faa0cfbe8dc891b6
```

Источник файла и контрольной суммы — [релиз Cloudflare на GitHub](https://github.com/cloudflare/cloudflared/releases/tag/2026.10.1).
Глобальная установка, Windows service, Cloudflare login и регистрация домена не
нужны. Каталог `outputs/` игнорируется Git. При переносе репозитория binary надо
скачать заново с указанного релиза; можно передать его путь через `-CloudflaredPath`.
Для другой версии сначала проверить опубликованный SHA-256 и указать
`-ExpectedSha256` с проверенным значением; совпадение неизвестной локальной суммы
само по себе не подтверждает происхождение файла.

## Проверка без публикации

Из корня репозитория сначала запустить локальную модель и API по
[инструкции сервиса](forte_service.md). Не запускать вторую модель, если GPU уже
занят другим чатом. Затем в отдельном PowerShell:

```powershell
& 'scripts/start_forte_tunnel.ps1' -CheckOnly
```

Ожидается `LOCAL_CHECKS_PASSED_NO_TUNNEL`. Проверяются SHA-256 binary,
`/healthz` с `model_ready=true` и отказ HTTP 401 при обращении к API без ключа.
Если модель выключена или восстанавливается, скрипт завершится без публикации.

Если политика PowerShell запрещает локальные скрипты, можно выполнить разовый
запуск без изменения системной политики:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File scripts/start_forte_tunnel.ps1 -CheckOnly
```

## Запуск после согласования маршрута

```powershell
& 'scripts/start_forte_tunnel.ps1' -AllowExternalTraffic
```

Будет напечатан временный HTTPS URL. Появление адреса означает выдачу имени,
а не подтверждённую доступность из Интернета. Скрипт оставляет терминал занятым,
а собственный процесс `cloudflared` запускает без отдельного окна. Ключ API
скрипту не передаётся; он не читает и не выводит `operator-key.txt`.

В текущей сети ноутбука первый запуск через QUIC не дал рабочего внешнего
соединения: адрес возвращал HTTP 530. Поэтому launcher явно использует
`--protocol http2`; с ним проверка внешнего HTTPS-адреса прошла. Это транспорт
соединения cloudflared с Cloudflare, а origin остаётся локальным HTTP на порту 8000.

При нестандартном порте локального API:

```powershell
& 'scripts/start_forte_tunnel.ps1' -Port 8001 -CloudflaredPath 'C:\tools\cloudflared-windows-amd64.exe' -AllowExternalTraffic
```

Порт 8777 запрещён. Адрес origin всегда `127.0.0.1`; параметры не позволяют
направить туннель на удалённый сервер. Скрипт использует отдельный пустой config,
чтобы не загрузить чужие ingress-настройки, убирает у дочернего процесса переменные
`FORTE_*`/`TUNNEL_*` и не включает debug-логи с HTTP-заголовками. Журналы и PID
своего процесса находятся в `outputs/forte-tunnel/runs/<run>/`; ключи в metadata
не записываются. Файл блокировки предотвращает второй экземпляр этого launcher.

## Проверка перед отправкой жюри

С другого устройства через другую сеть, например мобильный Интернет:

1. Открыть HTTPS URL и проверить страницу загрузки.
2. Проверить `/healthz`: HTTP 200 и `model_ready=true`.
3. Проверить API без `X-API-Key`: HTTP 401.
4. Сначала отправить только разрешённый синтетический MOV с ключом в заголовке;
   получить HTTP 202 и `job_id`, затем опрашивать `GET /api/v1/jobs/{job_id}` с тем
   же ключом. На синтетическом видео допустим `failed`: здесь проверяется связь.
5. После разрешения передачи конкурсных данных проверить MOV требуемого размера,
   конечный JSON, изображения и полное время от загрузки до результата.

Browser login, email OTP и `--allowed-mail` не включаются: API должен принимать
обычный `X-API-Key`. Страница, health и справочник правил доступны по URL всем;
загрузка и результаты требуют ключ. Передать жюри URL и ключ по согласованному
каналу, не помещать ключ в URL, Git или общедоступный README. Публичная доступность
не подтверждает качество распознавания.

Синтетическую проверку можно воспроизвести локальной командой, подставив выданный
HTTPS URL. Скрипт сам создаёт 29 MiB заведомо повреждённых байтов; он не читает
конкурсные видео. Ожидаются 202 при загрузке и конечный `failed` без вердикта.

```powershell
& 'outputs/forte-api-validation/20261018/.venv/Scripts/python.exe' -B scripts/check_forte_endpoint.py --base-url 'https://YOUR-URL.trycloudflare.com' --key-file outputs/forte-service/operator-key.txt --output outputs/forte-service-checks/external-001.json --upload-mib 29
```

Используйте новый путь отчёта для каждого запуска. Ключ берётся из локального
игнорируемого Git файла и передаётся только в заголовке; отчёт содержит численные
статусы и время, без секретов и тел ответов. Для проверки на ноутбуке замените
`--base-url` на `http://127.0.0.1:8000`. Утилита прошла 16 синтетических проверок,
включая реальные обращения к собственному локальному mock-серверу с 1 KiB и 29 MiB.

## Ограничения

- Адрес действует, пока запущен `cloudflared`, и меняется при новом запуске.
  Гарантии uptime нет; Quick Tunnel предназначен для тестирования. Для постоянного
  адреса нужен другой способ размещения. Аккаунт и собственный домен для Quick
  Tunnel не требуются. [Официальное описание](https://developers.cloudflare.com/tunnel/get-started/quick-tunnels/)
- У Quick Tunnel максимум 200 запросов в обработке, сверх лимита — 429; SSE не
  поддерживается. Наш API использует POST и опрос GET, а локальная очередь принимает
  только одну активную задачу. [Ограничения Quick Tunnel](https://developers.cloudflare.com/tunnel/get-started/quick-tunnels/)
- В общей таблице Cloudflare указан максимум загрузки 100 MB для Free/Pro.
  Отдельный гарантированный предел для accountless Quick Tunnel в проверенной
  странице не указан. Практический ориентир для демонстрации — MOV **до 95 000 000
  байт**, чтобы оставить место multipart; это запас, а не подтверждённый лимит
  нашего адреса. Локальное ограничение API 128 MiB не отменяет ограничения внешнего
  прокси. Ошибку 413 нельзя считать результатом анализа. [Размер загрузки](https://developers.cloudflare.com/support/troubleshooting/http-status-codes/4xx-client-error/error-413/)
- Ноутбук должен оставаться включённым, подключённым к питанию и Интернету.
  Сон, разрыв сети, остановка модели или терминала нарушают доступность. Время
  загрузки по внешней сети прибавляется к времени обработки; фактические пять минут
  нужно проверить отдельно.

## Остановка

Нажать Ctrl+C в терминале туннеля. `finally` завершает только сохранённый handle
дочернего `cloudflared`; другие процессы, API и GPU-модель не останавливаются.
Нельзя использовать `Stop-Process -Name cloudflared` или завершение всех Python.

После принудительного убийства самого PowerShell выполнение `finally` не
гарантируется. Если дочерний процесс остался, прежде чем завершать его вручную,
сверить **PID, время запуска и путь executable** с `connection.json` именно этого
запуска: один PID может быть повторно выдан чужому процессу. После остановки адрес
перестаёт работать. Локальные журналы остаются для диагностики; не публиковать их.
